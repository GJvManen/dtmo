# RUN-20260810-169 — Search and live intelligence ingestion remediation

## Objective

Restore one bounded, user-blocking functional path after external/local acceptance feedback: **search plus the existing CISA KEV live connector must form an end-to-end provenance-preserving ingestion and search pipeline**. Admin configuration/source-registry UX, additional source types, and graphical dashboard integration are deliberately backlog items for subsequent bounded runs.

## Plan

Blocking observations on the accepted 16.0.0rc6 baseline:

1. `/api/v1/intelligence/search` returned `503 search backend unavailable: HTTPStatusError` on a fresh deployment when `dtmo-intelligence-v1` did not yet exist.
2. The OpenSearch index used `dynamic: strict`, but its mapping declared `confidence` while the canonical ingestion path indexed `confidence_score`, `confidence_level`, and `confidence_rationale`. OpenSearch documents that a strict dynamic mapping rejects unmapped fields, so this contract could make indexing fail closed.
3. `run_cisa_kev()` fetched and parsed the authoritative CISA KEV feed but did not land, persist, or index the records. Successful connector execution therefore did not make intelligence searchable.
4. The manual connector-run endpoint was not permission-gated. Exposing a live-fetch control without `manage:connectors` would violate least privilege.
5. Existing canonical records whose previous index write failed needed an idempotent repair path rather than duplicate database records.

External gates in issue #1 remain unchanged. This run does not claim genuine staging, assistive-technology, penetration-test, external-assurance, or production evidence.

## Do

Implemented on `release/16.0.0rc7-intelligence-pipeline`:

- `OpenSearchService.search()` now ensures the index exists before querying, making empty fresh deployments return an empty result set instead of surfacing an index-not-found HTTP error.
- The strict mapping now matches the canonical document contract: `confidence_score`, `confidence_level`, and `confidence_rationale`; search sorting uses `confidence_score`.
- Canonical ingestion always performs idempotent PUT-by-ID indexing, including duplicate/replayed records, so a connector replay can repair an earlier search-index failure without duplicating the database object.
- The existing CISA KEV connector now feeds every successful record through the same raw-lake, canonical persistence, provenance, and OpenSearch path as governed ingestion.
- Connector-originated records are attributable to `connector:<connector-id>`, preserve source reliability and raw payload provenance, and remain unreviewed/unshared by default.
- Manual CISA KEV execution now requires `Permission.MANAGE_CONNECTORS`; ADMIN and dedicated service-account policy retain that permission, while publication/share approval remains human-governed and separate.
- Added regression tests for empty-index search initialization, strict mapping compatibility, canonical search sorting, and connector persistence/indexing orchestration.
- Version advanced to `16.0.0rc7`.

## Threat, vulnerability, and vendor review

Reviewed 2026-08-10 using primary/authoritative public sources:

- **OpenSearch official mapping documentation** — `dynamic: strict` rejects documents containing fields that are not explicitly mapped. Applicability: **direct / high confidence**; this explains the mapping-contract failure mode addressed in this run.
- **OpenSearch official version history** — the repository currently uses OpenSearch 2.19.1 while the 2.19 line has later patch releases including 2.19.6 (2026-07-02) with security updates. Applicability: **deployment dependency / high confidence**. This run does not change the pinned platform version because dependency upgrade and compatibility/security validation is a separate bounded objective; the upgrade remains a production-readiness backlog item.
- **CISA KEV catalog and CISA-maintained `cisagov/kev-data` mirror** — CISA identifies KEV as an authoritative input for vulnerabilities known to be exploited in the wild; the mirror states it tracks the canonical catalog and is updated shortly after it. Applicability: **direct connector provenance / high confidence**.

No claim is made that this review proves absence of vulnerabilities or substitutes for dependency scanning, penetration testing, or deployment-time advisory review.

## Act

Lessons:

1. Connector success is not useful evidence unless records cross the canonical persistence/search boundary.
2. Strict search mappings require schema-contract regression tests whenever canonical fields change.
3. Empty deployments must have defined query semantics; an absent index is an empty-data state, not automatically an operator-visible backend failure.
4. Replay must repair derived indexes idempotently without changing governance state.
5. Live-source controls are privileged operations and must never be exposed as anonymous convenience endpoints.
