- route: `POST /connectors/cisa-kev/run`;

- affected bucket: `dtmo-raw`.

A repeated CISA attempt later in the same run failed at the same object-store authentication boundary.

## Repository root cause

The failure is reproducible from the source-controlled local development configuration:

1. `.env.example` supplied the API with `DTMO_MINIO_ACCESS_KEY=dtmo` and `DTMO_MINIO_SECRET_KEY=change-me-now`;
2. `docker-compose.yml` starts local AIStor with separately required `MINIO_ROOT_USER` and `MINIO_ROOT_PASSWORD`;
3. local Compose contained no service or script provisioning the `dtmo` application identity in AIStor;
4. therefore a fresh-clone operator could provide valid AIStor root inputs and still have the API authenticate with unrelated default credentials.

The previous owner instruction to skip an earlier `.env` mistake remains historical context, but the new fresh-clone evidence plus repository inspection establishes an independent source-controlled configuration mismatch.

## Repair boundary

Branch: `rc13/local-objectstore-credential-contract`

The bounded repair:

- makes local-development Compose explicitly pass `MINIO_ROOT_USER` / `MINIO_ROOT_PASSWORD` to the API as `DTMO_MINIO_ACCESS_KEY` / `DTMO_MINIO_SECRET_KEY`;
- removes misleading runnable `dtmo/change-me-now` object-store defaults from `.env.example`;
- documents that this credential reuse is **local development only**;
- leaves production/staging architecture unchanged: the staging emulator still requires distinct least-privilege `AISTOR_APP_ACCESS_KEY` / `AISTOR_APP_SECRET_KEY` credentials;
- extends object-storage contract tests for both local consistency and staging separation;
- adds an exact-head workflow that renders `docker compose config` and verifies the effective API/AIStor credentials match locally.

This local-development exception does not grant publication authority and does not weaken the production/staging least-privilege requirement.
