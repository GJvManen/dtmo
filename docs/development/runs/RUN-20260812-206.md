## Owner-observed blocker 1 — NVD non-HTTP upstream reference used as canonical URL

At `2026-08-12T11:33:48.217467Z`, `POST /api/v1/admin/sources/nvd-cve/run` returned HTTP 500.

The exception was a Pydantic `ValidationError` for `IntelligenceIngestRequest`:

- `canonical_url`: URL scheme must be `http` or `https`;
- `provenance.0.source_url`: URL scheme must be `http` or `https`;
- the rejected source value was an NVD upstream `ftp://ftp.freebsd.org/...` reference.

Repository inspection confirmed the NVD parser can replace the stable NVD CVE detail URL with the first external reference. NVD raw references are third-party evidence and can legitimately use a non-HTTP scheme. They must not weaken the canonical HTTP(S) URL contract.

### Repair boundary

For `nvd-cve` records with a valid CVE identifier, canonical/provenance URL must remain:

`https://nvd.nist.gov/vuln/detail/<CVE-ID>`

All upstream references, including FTP references, remain preserved in raw evidence. The `HttpUrl` HTTP(S)-only schema is not relaxed.

## Owner-observed blocker 2 — supported advisory alias not in canonical enum

The same retest showed supported advisory records using `item_type='security-advisory'` failing persistence because the canonical SQLAlchemy enum `intelligence_type` does not contain that value.

Repository inspection confirmed canonical `IntelligenceType` values are:

- `incident`;
- `advisory`;
- `vulnerability`;
- `malware`;
- `campaign`;
- `vendor-notice`.

Supported adapters including RSS, Chrome, Mozilla, NCSC CSAF, CERT-EU and MSRC have historically emitted the semantic alias `security-advisory`.

### Repair boundary

At the canonical connector ingest boundary:

- explicitly supported alias `security-advisory` normalizes to canonical `advisory`;
- already-canonical values remain unchanged;
- unknown connector object types remain fail-closed and are not silently coerced.

This preserves semantic meaning while aligning source records with the persisted domain model.
